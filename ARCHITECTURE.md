# Architecture

<!-- keel:architecture-schema 1 -->

## Overview

The Go service lives in `backend/` (its own `go.mod`, `Makefile`, config and Docker files) and the Next.js app in `frontend/`; paths such as `cmd/backend` or `config/.env` below are relative to `backend/`.

**Confirmed.** Dataset runs as two long-lived processes plus Postgres: `cmd/backend` serves Fiber HTTP (health, auth, sessions, preferences, notifications, users, audit, collections and records); `cmd/mailer` claims `sys.outbox` rows under a 10-minute lease (`SKIP LOCKED`), opens the sealed token and sends SMTP. `cmd/admin` handles operator actions. `frontend/` is a Next.js BFF: it keeps the tokens in a signed httpOnly cookie, forwards API calls with the bearer and sends the client IP as `X-Real-IP`, which the backend accepts only from the web container's fixed address (`API_TRUSTED_PROXIES`). Composition wires use cases to Postgres. Product constraints live in `PRODUCT.md`; surface briefs in `.keel/surfaces/`.

## Boundaries

**Confirmed dependency direction (as coded):**

```text
cmd → composition / infra / adapter/inbound / config / pkg
infra → adapter/outbound/persistence/postgres (opens the connection)
composition → core/usecase + adapter/outbound
adapter/inbound → port/input (+ pkg/apperror)
adapter/outbound → port/output + domain
core/usecase → domain + policy + ports + pkg/{apperror,password,tokenhash,validate,clientip}
core/domain → stdlib only
```

| Boundary | Owns writes | Notes |
|----------|-------------|--------|
| `internal/core` | — | Domain + ports + use cases; no Fiber/GORM/config |
| `adapter/inbound/http/rest` | — | DTOs, route map, `apperror`→HTTP |
| `adapter/outbound/persistence/postgres` | `usr.*`, `sys.outbox`, `app.collection`, `app.collection_member`, `app.record` | GORM/`Exec`; `Store` = TxManager + UnitOfWork |
| `frontend/` | session cookie only | Next.js; never reaches Postgres, holds no signing key |
| `cmd/mailer` | outbox claim → SMTP | Poll 2s, batch 10; terminal fail after 14 attempts or smtp_disabled |

**Sacred (product + ADR):** JWT must not carry permission claims; authz loads live from the DB on each check. Plaintext passwords / refresh JTIs / email tokens must not be stored.

**Authorization (confirmed):** Authorizer is applied on `/v1/users` and `/v1/audit`; own-account routes live under `/v1/me`, use Bearer and queries scoped to the authenticated user; `/v1/auth` keeps only the token and sign-up flows. Platform roles (`usr.role`, its permissions and members) have no HTTP routes: the default `user` role covers every account, and `cmd/admin` promotes or demotes a platform admin (`is_superuser` or a `*` grant); the API never grants `*`. A grant's resource is one of `*`, `audit`, `collections`, `roles`, `users` (`chk_usr_role_permission_resource`; a new resource widens that CHECK in a new migration). Collection access is per collection (below). Users with a protected role get the same treatment under `/v1/users`: not listed, 403 by id, changed only through `cmd/admin`. Nobody disables their own account. Enable puts an account back to `active`, or `pending` if it never set a password; sessions do not come back.

**Collection membership (confirmed):** collections and records are not governed by RBAC but by `app.collection_member` (fixed roles: `owner` changes fields, settings and members; `editor` writes records; `viewer` reads). RBAC keeps only `collections:create`, which the default `user` role holds (seeded in migration `000002`), so every account may start collections. Activating an account that belongs to no collection (a self sign-up, or an invite from the users screen) creates a starter collection it owns, named in the account's language with a required title and notes (`policy.GiveStarterCollection`, `domain.StarterCollection`), in the activation transaction; someone invited into a collection starts there instead. `/v1/collections` and `/v1/records` run behind Bearer (the record routes under a collection's address also take an API key, see Addresses) and the use cases call `policy.CollectionRole` per request: a non-member gets 404 (existence does not leak), a member with too small a role 403. A platform admin (enabled `is_superuser` role or a `*` grant) sees every collection as owner. The creator becomes owner in the create transaction; a collection keeps at least one owner (member changes take a per-collection advisory lock). `POST /v1/collections/{owner}/{slug}/members` adds an account by email or, when none exists, invites it (`auth.Invite`, pending account) and adds it at once; the invite and the membership are two transactions (marked `shortcut:`). Collection names are no longer unique across the instance, so a hidden collection neither blocks nor reveals a name.

**Addresses (confirmed):** a collection lives at `/<owner>/<slug>`, in the app and in the API (`/v1/collections/:owner/:slug/...`), as repositories do on GitHub; ids stay for records (`/v1/records/:id`), files, bulk calls (`ids` in the body) and deleted collections (`/v1/collections/trash/:id`), which give their address up. Every account has a `username` (`usr.usr_user.username`, 1-39 lowercase letters, digits and inner hyphens; `domain.ValidUsername`, mirrored by `usr.fn_username_reserved` for the reserved words, which include the frontend's top-level routes), made from the email by a trigger, optionally chosen on `POST /v1/auth/activate` (`username`; at activation, not signup, so only the email's owner claims a name, and a taken one answers 409 with the account still pending) and changed on `PATCH /v1/me`. A collection's `owner_id` is the account in its address and `slug` is its name slugified (`app.fn_collection_path`), unique among the owner's live collections as on GitHub: a create, rename, duplicate, transfer or restore whose name gives a slug the owner already has answers 409 `ALREADY_EXISTS` on `name` (`uq_app_collection_owner_slug`, mapped in `shared.WrapError`). The address owner stays an owner member until `POST .../transfer` hands the address to another owner member; removing or demoting it is refused (409). Renames, transfers, restores and username changes keep the old address in `app.collection_path`, so an old address still answers (`middleware.CollectionPath` resolves `:owner/:slug` to the id, current addresses before old ones, then the use case checks access by id as before, so a hidden collection reads as missing); the app's pages move to the current address. Record routes under the address take an API key; the rest of the collection's routes need a session, and they are registered after the record routes so the session check does not refuse a key. Responses that point at a collection known by id carry its address instead of making the app look it up: record backlinks (`owner`, `slug`), audit entries about a collection (`target_owner`, `target_slug`) and notifications whose params name one (`collection_owner`, `collection_slug`, read with the list, empty once it is deleted). The app has no `/collections/<id>` page; a record known only by id (a reference value, a Markdown link) opens through its permalink `/records/<id>`, which finds its address.

**Collection monitoring (confirmed):** `GET /v1/collections/{owner}/{slug}/audit` (owners) is the audit log filtered to the collection: entries whose target is the collection (its changes and member changes) or whose `details.collection_id` names it (record create, update and delete); `idx_sys_audit_log_collection` serves the second. `GET /v1/collections/{owner}/{slug}/quality` (editors and owners) walks the records by id (`idx_app_record_collection_id`) in batches of 500 and checks each against the current schema with `schema.Check`, returning the count and the first 100 invalid records with their issues; the ids it keeps for "delete invalid" stop at 10 000 (`domain.QualityMaxInvalidIDs`, a CHECK on `app.collection_quality`). It runs as a background job and stops at 500 000 records (marked `shortcut:`).

**Collection overview, icon and leave (confirmed):** `GET /v1/collections/{owner}/{slug}/stats?tz=` (any member) returns the record and member counts, the last record update, records created per day over the last 30 days in the caller's time zone (an IANA name, default UTC) and the top contributors by `record.create`/`record.update` audit entries in the same window. `POST /v1/collections/{owner}/{slug}/leave` removes the caller's own membership and is refused (409) for the last owner. Leaving or being removed also takes the collection out of that person's API keys, so coming back does not revive them. `app.collection.icon` holds a slug from a fixed allowlist (`domain.ValidCollectionIcon`, mirrored by `frontend/src/lib/collection-icons.ts`); empty shows the initials. **Record tools (confirmed):** `GET /v1/collections/:owner/:slug/records/export?format=jsonl|csv&valid=` (viewers) streams every record in batches (keyset scan; the stream has its own 10-minute write deadline over the server's 30 s write timeout, and the web proxy limits only the wait for the headers); CSV columns follow the schema's property order (`schema.PropertyOrder`) and every cell goes through `mapper.CSVCell`; null and a missing value both export as an empty cell, so only JSON Lines keeps null through an export and import. `POST /v1/collections/:owner/:slug/records/import` (editors) takes one batch of up to 5000 records under the 8 MB body limit. The browser reads the file in a Web Worker (`lib/import.worker.ts`, driven by `lib/import-client.ts`), so the page keeps answering: CSV, JSON Lines, a JSON array (`JsonArrayReader`, which splits the items by tracking brackets and strings) and the first sheet of an .xlsx (`xlsxRows`, `lib/xlsx.ts`: the zip's central directory is read by `Blob.slice`, the sheet streams through `DecompressionStream`; the shared strings are held whole, zip64 is not read) stream in pieces (`lib/import-stream.ts`), batches of up to 5000 records or 4 MB are made one at a time and wait for the page to finish each, so memory holds one batch whatever the file's size; the file is read twice, a `dry_run` pass that checks every batch, then the pass that sends them. Lines that are not JSON and records over 1 MB are reported by the browser, since the server sees one batch at a time; without an upsert key, so is a unique field's value an earlier line already holds (the first 2 000 000 values are remembered, past that the server refuses the repeat). With an upsert key the browser leaves unique values to the server, since only it knows whether an update keeps or releases a value: rows repeating an upsert key are applied in order (the batch is cut into segments with one change per record, each staged in the import's transaction so the next one matches it), updates are saved together with each record's expected version (`UpdateMany`, 409 if another writer changed it), and equal values are compared by PostgreSQL's jsonb equality (`UniqueValues`). A `dry_run` runs the same steps and rolls the transaction back. Numbers that would lose digits in a JavaScript number (16 or more digits, or a 3-digit exponent) are sent as the file wrote them (`sourceJSON`). Each sent batch carries `batch_key` (`<file id>:<batch number>`, up to 100 printable characters): the server claims it in `app.import_batch` inside the import's transaction (`ClaimImportBatch`, insert-or-nothing), and a key it already holds answers with the stored counts and `replayed: true` without saving again, so a batch whose answer was lost is never saved twice; a batch that saved nothing frees its key, and the hourly sweep drops keys older than 7 days (`PruneImportBatches`). The browser retries a 429 after its `Retry-After` (up to 30 times) and a network error, 408 or 5xx after 2, 4, 8… seconds (up to 8 times, `withRetry` in `lib/import-client.ts`); after each batch it notes the batches sent in localStorage (`dataset.import-progress`, per collection, fields, file name, size, date, columns and upsert key, kept a week; the fields type the values and so decide where batches are cut), so Stop, a closed tab or a failure keeps what was sent, and choosing the same file again skips those batches in both passes; at the end, records checked as valid but not created or updated raise a warning. Creating a collection from a file infers its fields in the same worker in one pass (`SchemaInferrer`, a summary per field, not the values); the `'` the CSV export puts before a cell starting with `=`, `+`, `-` or `@` (`mapper.CSVCell`) is dropped again when reading a CSV (`parseCsv`), so negative numbers and phone numbers come back as they were; a field that is null in every record of a file is inferred as text that also takes null; CSV and Excel object/list cells are decoded as JSON using the storage schema, including nullable types, alternatives and local references; collection creation from CSV/JSON infers object properties and list items recursively across the file, including optional subfields and empty structures; batches commit one by one. `GET /v1/collections/:owner/:slug/records?filter={...}` matches exact top-level values with `data @> filter` on `idx_app_record_data_path` (GIN `jsonb_path_ops`). Every change that replaces a record's data (edit, restore, bulk fix) first saves the old data in `app.record_version` (kept forever, marked `shortcut:`); `GET /v1/records/{id}/versions` and `POST /v1/records/{id}/restore` read and restore them, and a restore must match the current schema. `POST /v1/collections/{owner}/{slug}/quality/fix` (editors) fills, renames or removes one top-level field in every record without checking the schema. The quality check is a background job (`collection.quality`) storing its result in `app.collection_quality`: `POST /v1/collections/{owner}/{slug}/quality` starts it unless one started less than 15 minutes ago is running; a bulk fix or delete-invalid starts one even then, and the run it replaces may have read the records before the change, so a job stores its result only while its start (`started_at`, carried in the job) is still the latest; `GET` reads it, and a result of an older collection version is stale; `POST /v1/collections/{owner}/{slug}/quality/delete-invalid` deletes the records that result found invalid, except those changed after it started. `POST /v1/collections/{owner}/{slug}/duplicate` needs the right to create collections and read access to the source. Adding a member notifies them (`collection_added`).

`GET /v1/collections?details=true` adds `member_count`, `field_count` and `last_activity` (newest change to the collection or its records); only the collections screen asks for them, which groups up to 100 collections in the browser into favorites, the caller's own (owner), shared with them and, for a platform admin, the others. Pinned collections and keyboard shortcuts (`g`+key to a section of the selected collection, `?` for the list) live only in the browser: pins in the UI store (localStorage).

## Data

**Confirmed stores:**

| Store | Role | Consistency notes |
|-------|------|-------------------|
| PostgreSQL schemas `usr`, `sys`, `app` | Source of truth | Single DB; migrations 000001–000005 (squashed before the first release: each table created in its final form) |

**`usr` ownership (backend auth and account use cases):** users, credentials, sessions, email tokens, login attempts, role assignment, preferences, notifications; RBAC reader uses `vw_user_effective_permissions` + `is_superuser`.

**`sys.outbox`:** backend INSERT on register / password-reset; mailer claims `pending` → `processing` (lease in `available_at`, ownership in `claim_id`; a crashed claim returns and stale confirmations are rejected) → `sent`/`failed`. Tokens stay AES-GCM sealed with `SMTP_MASTER_KEY` and leave the row when done. `sys.fn_cleanup()` drops history older than 30 days; the backend's job worker calls it every hour (`job.Repository.Cleanup`), so Postgres needs no extension for it.

**`app.product`:** removed before the first release; the module's files are in git history (commit `eab7529` and earlier).

**`app.collection` / `app.record`:** a collection holds a JSON Schema in a `json` column, not `jsonb`: jsonb sorts object keys by length, and the key order of `properties` is the field order of the generated form. A record's `data` is `jsonb` (≤ 1 MB uncompressed, `chk_app_record_data_size`, `domain.RecordMaxBytes`; a write over it answers 422 on `data`, and import refuses such a record alone, `Records.Oversized`), checked by `pkg/schema` inside the write transaction after reading the schema `FOR SHARE`, so a concurrent schema change waits. A schema change does not revalidate stored records (marked `shortcut:`); the schema it replaced is kept in `app.collection_schema_version` (`GET .../schema-versions`, owners) and the Fields page loads one back into the editor. Deleting a collection sets `deleted_at`/`deleted_by` (every collection query filters `deleted_at IS NULL`) and keeps its records. The record list returns a preview (top-level plain values, strings cut to 120 characters, `{id,name}` of an object holding both (an attached file), and the first 10 of a list of strings or of such objects); `GET /v1/records/{id}` returns the full data. Access to both follows collection membership (see Authorization). In the browser, `frontend/src/lib/schema-validator.ts` validates with `@cfworker/json-schema`: ajv compiles with `new Function`, which the production CSP blocks. Compiled schemas are cached by content hash (512 at most) in `pkg/schema.Compile`. An update first saves the replaced data in `app.record_version`; a record keeps its latest 100 versions, older ones are deleted on the next update. `GET /v1/collections/:owner/:slug/records/export` streams JSON Lines or CSV in id-ordered batches of any size (the CSV columns past the form come from the distinct top-level keys, up to 1 000). A share form (`dss_` form link) leaves required reference and file fields optional, since its filler cannot pick or upload them; Quality then lists those records. Quality's leftover check walks groups and lists of objects too, so a removed subfield is reported by its path.

**Trash:** deleted records move to `app.record_trash` in one statement (their `app.record_version` rows stay: the foreign key was dropped so a restore keeps the history). Editors list and restore; owners purge. A restore whose unique value another record took since is refused (409, `details.fields`); `values` in the restore body, for one record and only its unique fields, gives it new values that must fit the field and be free, saved as an edit (the trash page asks for them). `app.fn_purge_trash()` (the same hourly worker call) deletes trashed records and collections older than 30 days, with their versions.

**API keys and webhooks:** `app.api_key` keeps the SHA-256 of a `dsk_` key and its first 12 characters. A member makes keys for themselves on the API access page (`/v1/me/keys`, 20 per member), each with an optional end date (`expires_in_days`, 1-365; `expires_at`, after which the key no longer authenticates; `renew_days` on PUT sets a new end from now, 0 for none, and brings an expired key back) and picks the collections each reaches in `app.api_key_collection` (up to 50), each read (viewer cap) or write (editor cap, needs the editor role). The key acts as that member, so their role in each collection still applies, and stops when they are disabled. A collection's owner sees the keys that reach it and can take the collection out of one; every change logs to the collections it touches. Only the record routes (`/v1/records`, `/v1/collections/:owner/:slug/records`) and `/v1/files` take a key (`Authorization: Bearer dsk_…` or `X-API-Key`); audit entries name the key. `app.webhook` keeps the URL, events and the `whsec_` secret sealed with the SMTP key. A record change enqueues one `webhook.deliver` job per matching hook inside its transaction (`policy.Notify`); the job worker POSTs it with `X-Dataset-Event` and `X-Dataset-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">`, retries like any job and stores the last status. Limit: 10 hooks per collection. `failures` counts failed calls in a row (a success resets it); the 10th sets `paused_at`, notifies the hook's maker once (kind `webhook_paused`) and leaves the hook out of new events, and a queued call of a paused hook is dropped, so a dead receiver stops filling the job queue. `PATCH .../webhooks/:hookId` changes the URL and events (the secret stays) and pauses (`enabled: false`) or resumes it (clears `paused_at` and `failures`). The web proxy passes a key through as it is, so programs use the web address.

**MCP:** `POST /v1/mcp` serves the Model Context Protocol (streamable HTTP, stateless, JSON answers; `internal/adapter/inbound/mcp`, on the official Go SDK) for AI assistants. It takes an API key only, and its read tools call the same services as the REST routes, so the key's scopes and its maker's roles apply: `workspace_overview` (the starting point: every collection the key reaches with its description, access, record and trash counts, newest record change, fields summarized from the schema by `schema.Fields`, the subfields of groups and lists the same way, and which reachable collections reference it; one query, `Collections.Overview`, with a count subquery per collection on the `collection_id` indexes), `get_collection` (the full JSON Schema, when the overview is not enough), `search_records` (text, rules and groups as in `where`, up to 50 a page; like `get_record`, `get_records` and `list_trash` it takes `fields` to cut each record's data to the named top-level fields with `domain.KeepFields`, after the read, to spare the model's context; listings of one collection leave out `collection_id`), `get_record`, `related_records` (records of other collections that reference it), `collection_stats`, `aggregate_records` (`Records.Aggregate` with a `domain.GroupQuery`: count, and sum/avg/min/max of up to 5 number fields, in total, per value of `group_by` (a list field counted per element, `Elements`, through a lateral `jsonb_array_elements`; the grid's grouping keeps whole lists, since picking a group filters with `eq`) or per `bucket` (day, week, month, year) of a date field, keyed by the span's first day; up to 100 groups), `field_values` (`Records.Stats` with `Top`/`Skip` and `Elements`, so list fields count per element: every value of one field, commonest first, up to 100 a page, with the filled and distinct counts; the instructions send the assistant there before it filters a text field), `get_records` (up to 50 by id, the missing ones listed), `record_history` (the current data and up to 50 saved versions, each with the top-level fields it changed, from and to) `list_views` (the saved views the member sees, their `where` in the shape `search_records` takes) and `search_everywhere` (free text in every collection the key reaches, one `Records.List` each, the total and newest 3 per collection with matches). `search_records` and `get_records` take `expand` (up to 5 reference fields, `field` or `field.subfield`): the referenced records come along in each record's `expanded`, read with `Records.List` by id per target collection (100 ids a call, as the key's member, so scopes apply; a target the key cannot read fails the call). With a write scope (and an editor role) `create_record`, `update_record` (merges top-level `set` values, `null` removes a field, refused when the record moved past the version read), `create_records` (up to 100 through `Records.Import`, all or none, the error naming each bad record by index), `update_records` (the same `set` on every record matching search and rules: a filter is required, `dry_run` gives the count and five of them, more than 100 matches refuse the call, then `Records.BulkUpdate` all or none), `delete_records` (names its `collection_id`; up to 100 records of that collection to the trash, all or none), `list_trash` (the newest 50) and `restore_records` (up to 100 back from the trash) change records. The MCP instructions and all built-in `collection_id` argument descriptions require the collection UUID copied from `workspace_overview`, never its name or slug. A malformed UUID returns an `INVALID_INPUT` tool error on `collection_id`, explaining how to call `workspace_overview` and retry with its `id`, before any lookup or write. A valid UUID outside the key answers as a tool error, "not found". Before running, the record tools check the field keys they are given (rules, `fields`, `group_by`, `numbers`, `field`, `sort`) against the collection's fields, and the values of `eq`/`neq`/`in`/`not_in` rules on option fields against the options (`mcp/check.go`): a slip that would match nothing in silence fails with the key or option to use (matched ignoring case and accents) and the valid ones; a collection without schema fields is not checked. The REST filter stays lenient, so saved views on removed fields still open. The server instructions lay out the steps: overview, `field_values` for text values, `search_records` with rules and `fields`, `aggregate_records` to count. The web proxy forwards `Accept` and `MCP-Protocol-Version`, so assistants use `<web address>/api/proxy/v1/mcp`. A POST that asks for JSON alone (Swagger) is let in, since answers are always JSON. For the API docs and quick tests, `GET /v1/mcp/tools` (tools/list) and `POST /v1/mcp/tools/{name}` (tools/call, the body holds the arguments) send one JSON-RPC call through the same handler and return its `result` without the envelope; Swagger takes the key as ApiKeyAuth (`X-API-Key`) in Authorize, beside the session token; the routes that accept a key list both schemes. **Owners' tools:** a collection owner publishes up to 20 read-only tools (`app.mcp_tool`, Integrations page): a name, a description the assistant reads, fixed conditions, up to 10 parameters (each bound to a top-level field and one of eq, neq, contains, gt, gte, lt, lte, in, has, typed from the schema when saved, required or optional), the fields returned (none: all), sort and page size (up to 50), plus a `page` argument. Each MCP request builds its server with the built-in tools and the enabled owners' tools of the key's collections (a name two collections share goes to the older tool); a call runs `Records.List` as the key's member with the fixed conditions AND one rule per given argument, so scopes and roles apply as for `search_records`. No code or SQL is stored: the settings are conditions the record filter already validates. `POST .../mcp-tools/test` runs unsaved settings once with sample arguments, as the owner. **Call log:** a receiving middleware writes each `tools/call` to `app.mcp_call` (tool, key, member, ok or the first 200 characters of the error, and the arguments as JSON cut to 500 characters, shown without the `collection_id` under each call) for every collection the call acted in: one named in `collection_id` that the key reaches, or one a tool marks (`get_record`, `update_record`, `record_history`, owners' tools). Calls that name no collection (`workspace_overview`, `related_records`) are not logged. Owners read the newest 100 (`GET .../mcp-calls`); a member reads the newest 100 of one of their keys across collections (`GET /v1/me/keys/:keyId/calls`, "Usage" on the API access page); the hourly sweep drops rows older than 30 days. The API access page (`/api-access`) shows the MCP address, client snippets filled with a key just made, and a connection test that calls `tools/list` and `workspace_overview` with a key; once it connects, the "Testar tools" section (`components/mcp-tool-tester.tsx`) lists the key's tools by kind (read, write, owners'; `MCP_READ_TOOLS`) with a search, and runs any of them: a form built from the tool's `inputSchema`, where the record tools' known arguments get pickers from the overview's fields (`field`, `group_by`, `sort`, `order`, `fields`, `numbers` with number fields, `expand` with reference fields, `bucket` only for a date `group_by`) and `rules`/`groups`/`any` the rules editor (`RecordRules`), or the arguments as JSON. It sends `tools/call` with that key, so calls show in the key's usage, and shows the answer's size with a token estimate (characters / 4), the JSON-RPC request and its curl (key as `$DATASET_KEY`), and the last 10 calls to reopen, kept in page memory only like the key. Writing tools ask first unless `dry_run` is on. Its OpenAI API example allows the read tools only (`allowed_tools`), since it skips approval. **OAuth (the ChatGPT app):** clients that cannot take a pasted key use the authorization code flow with PKCE (S256), stateless: a 401 from `/api/proxy/v1/mcp` carries `WWW-Authenticate: Bearer resource_metadata=...`; the web app serves `/.well-known/oauth-protected-resource[/api/proxy/v1/mcp]` and `/.well-known/oauth-authorization-server`, and forwards `/oauth/register` and `/oauth/token` to `/v1/oauth/register` (RFC 7591; the `client_id` is the client's name and redirect URIs sealed with the SMTP key, https or http on localhost) and `/v1/oauth/token`. `/oauth/authorize` is a page of the signed-in app: the member picks the key's name, validity and collections, `POST /v1/oauth/approve` seals a 5-minute code (member, client, redirect, challenge, scopes), and the token call checks client, redirect and verifier and runs `CreateMyKey` as the member; the access token is that `dsk_` key, listed with the member's keys. Nothing else is stored; a code works again until it expires (`shortcut:` in `usecase/integration/oauth.go`; PKCE keeps it to its client).

**Files and references:** `app.file` rows name files kept in the file store under `files/<id>` (8 MB each; the backend and the web proxy take bodies up to 8 MB + 4 KB). A top-level property with `x-file: true` stores `{id,name,size,type}`, or a list of them when the property is an array (several files, up to 20 in the field builder); one with `x-ref: <collection id>` stores a record id, or a list of ids. Saves check every one exists (issue keyword `exists`). `GET /v1/records/:id/links` lists the records of other collections pointing at one (backlinks, 20 per field). Downloads (`GET /v1/files/:id`, viewers) serve images inline and anything else as an `octet-stream` attachment with `nosniff` and a sandbox CSP. The job worker sweeps files hourly (`tools.SweepFiles`): a file row older than a day that no record, trashed record or record version names is deleted, and a trigger lists every deleted file row (a purged collection's included) in `app.file_gone` until its stored bytes are removed. The search for a name is a text scan (`shortcut:`).

**Fields the server fills:** `x-auto: "number"` (integer, the collection's highest plus one, records in the trash included, so a restored record never meets its number taken), `"created_by"`/`"updated_by"` (string, the user's name) and `x-formula: "<expression>"` (`pkg/schema/formula.go`: field keys, numbers, `"text"`, `TRUE`/`FALSE`, `+ - * /`, `&` joining text, comparisons and the functions `IF AND OR NOT COALESCE ROUND ABS MIN MAX CONCAT UPPER LOWER TRIM LEN TODAY DAYS DATEADD YEAR MONTH DAY`, checked when the schema is saved; the property's type, number, string (a date with `format: date`) or boolean, is what it holds, and a result of another type, a `format: date` result that is not a `YYYY-MM-DD` date, or none leaves the field out; `TODAY()` is the server's date at save time, so it does not move until the record is saved again) are filled on every create, update, restore, import and bulk edit before the schema check (`record/auto.go`, `pkg/schema/auto.go`); the form shows them read-only. A schema save that adds an `x-auto: "number"` field or adds or changes a formula enqueues `record.fill` (`record/backfill.go`): it numbers the records without a number in creation order and recomputes formulas, saving each changed record as an edit; `created_by` added later stays empty on older records (the record stores no creator). Import takes `upsert_key`, a unique field: a row whose value a record already holds merges into that record (`updated` in the answer). `x-private: true` keeps a top-level field off share links (below). `x-lookup: {ref, field}` shows a field of the record that one of this record's reference properties names (a list of values for a list of references); `x-rollup: {collection, ref, fn, field}` gives `count`, `sum`, `avg`, `min` or `max` of a number field over the records of another collection whose reference `ref` names this record. Both are computed when records are read (`record/virtual.go`: one query per lookup or rollup for a page, `LookupValues` by id and `Rollup` by containment on `idx_app_record_data_path`), only from collections the reader may view, and every write drops them; conditions filter by them (a subquery per record, see Conditions), but lists cannot sort or chart by them (`shortcut:`).

**Form layout keywords:** these do not affect validation; the web form reads them, and a change to them alone is a safe "display" change on the Fields page. `x-multiline: true` selects a long-text editor without imposing a character limit; an explicit `maxLength` remains an optional validation rule. Older schemas with `maxLength >= 500` still use the long-text editor, and their limits are shown in the field rules. `x-colors: {option: color}` gives a list option its color (gray, red, orange, amber, green, teal, blue, violet, pink) on chips, table cells and board lanes. `x-section: "<title>"` opens a titled block of the form at that top-level field; the next fields stay in it. `x-width: "half" | "full"` sets the field's share of the two-column form. `x-show-when: {field, op, value}` (`op` eq, neq, filled or empty) leaves the field off the form while the other field does not match; its value stays, and such a field cannot be required (`shows` in `frontend/src/components/field-builder.tsx`). `x-format: "compact" | "currency" | "percent"` and `x-decimals: 0-6` set how a number field (or number formula) shows on the record list, the record page and the charts (`fieldFigure` in `frontend/src/components/format-figure.ts`). `x-default: "today"` starts a date or date-time field of a new record at the date it is opened. `pattern` (strings) is plain JSON Schema: the server checks it.

**Comments:** `app.record_comment` holds notes on a record, oldest first (200 shown); any member writes, the author or an owner deletes.

**Share links:** an `app.share_link` row (`kind` `form` or `view`) with a sealed `dss_` token, kept apart from the personal keys in `app.api_key`, made by an owner, with an optional end (`expires_in_days`, 1-365; `expires_at`, checked with the keys'). `/v1/public/:token` (no session, rate limited) acts as the link's maker capped to the one collection: a form adds records, a view lists them read-only. Private fields leave the schema and the data, a form refusing them; a view of a collection with private fields does not search, since a search over the whole record would tell which records hold a hidden value. The web pages are `/f/<token>` and `/s/<token>`.

**Automations:** `app.automation` (20 per collection, owners): a trigger (`record.created`, `record.updated`, or `daily` at an hour), conditions (the list's `where` rules) and an action: `set_field` through bulk update; `notify`, an in-app notification to its maker; `email` to the maker or every active member (one per recipient per run, through the mail outbox with purpose `automation`, the message sealed like a token, linking to the collection or the one record); `webhook`, one queued call of one of the collection's hooks with event `automation.run` and the matching records; `create_record`, one record per match in a collection the maker edits, where a string value `{{field}}` copies that field of the match and `{{id}}` its id. A record change enqueues an `automation.run` job per enabled match (`policy.Notify`); the worker checks daily ones every minute. A run acts as its maker on at most 100 matching records, and its own changes start no automation (`policy.WithoutAutomations`). Each webhook delivery is logged in `app.webhook_delivery` (newest 50 shown per hook) and can be sent again.

**Saved views:** `app.saved_view` keeps a named list query string; a view is the user's own or shared (editors) with every member.

**Conditions:** the list's `where` is `{any, rules, groups}`: rules joined by AND or OR, and one level of groups, each a bracketed set with its own join, so `(a AND b) OR (c AND d)` fits. At most 20 rules across groups and 10 groups; `whereSQL` builds one bound condition. Operators: `eq neq contains not_contains starts_with gt gte lt lte between empty not_empty in not_in has has_any`. A `YYYY-MM-DD` value compares with the field's first 10 characters, so a date-time matches by its day; `{"today": n}` is the caller's today plus n days (`tz` on the request, UTC for automations and MCP), resolved per query by `record.resolveWhere` on a copy, so a saved view or automation keeps its relative dates. `$created_at` and `$updated_at` filter by the record's own dates. A lookup or rollup field filters through a subquery (`fieldSQL`) once the caller may view the collection it reads; otherwise the rule is refused (403). `contains` and `starts_with` on a stored field add `data::text ILIKE` so the trigram index can serve them. The web editor offers operators by kind of field, picks referenced records by name, toggles options, and reads dates as fixed or relative ("before today", "in the next 7 days"); a right-click on a list cell keeps or hides its value; text values suggest the field's commonest values (the stats endpoint). Rules can also be written as text, as in Jira (`components/rule-text.ts`): `status = pago e valor > 100 ou (cliente = "Ana" e vencimento < hoje)`, Portuguese or English words, AND binding tighter than OR, one level of brackets. The text is parsed into the same `where` and written back from it, so both editors edit one filter; a referenced record is written by its title and looked up on apply (exactly one match, else an error at its column). Applied rules sit in a bar of their own below the toolbar: plain AND rules as one chip each (field, operator, value), edited in place from the chip; a mix with OR or groups as one "advanced filter" chip that opens the editor; the apply button counts the records the edited rules keep (a `limit=1` list). The old field filter (`filter`, a containment match) stays in the API; the web app reads it from older links as "equals" conditions.

**Quality and leftover fields:** a removed field's values stay in the records. The quality check reports each top-level key the schema no longer has (keyword `additionalProperties`) unless the schema sets `additionalProperties` itself; the page groups issues by field and offers the matching bulk fix. It also reports references and files that no longer exist (keyword `exists`, `policy.MissingLinks`, the same check a write runs). The record form lists leftover keys with a button that drops them, and labels a reference to a deleted record. On a collection with records, the field editor offers only types that keep the stored values (`typesKeepingValues`). Opening the page runs a new check.

**Analysis and dashboard:** `GET /v1/collections/:owner/:slug/records/profile` profiles the selected records in up to three queries, whatever the number of fields: one row of fill counts, number ranges (min, max, average, sum) and first and last dates; the 8 commonest values and the distinct count of each value field (a window over `unnest` of the keys); and records per day, week, month or year of each date field (`date_trunc`; a date-time counts by its date, invalid dates are skipped with `pg_input_is_valid`, at most 2 000 buckets). The Analysis page is one call to it. A collection's dashboard is `app.collection_dashboard.widgets`, a JSON list of widgets (`count`, `sum`, `avg`, `min`, `max`, `bars`, `timeline`, `list`), each with a field, conditions and, for a timeline, a bucket; a `bars` widget may set `measure` and `fn` (`sum` or `avg`) to chart a number field per value with one `records.aggregate` call, and a figure widget may set `compare: {field, days}` to show the change against the same number of days before (two stats calls); owners replace it with `PUT /v1/collections/{owner}/{slug}/dashboard`, members read it, and each widget draws itself with one stats or list call. Analysis, widgets and automations can copy a saved view's conditions.

**Database roles:** migrations run as the owner (`POSTGRES_USER`). Backend and `cmd/admin` connect as `dataset_app` (`POSTGRES_APP_USER`), which reads and writes rows in `usr`, `sys` and `app` and cannot change the schema. The mailer uses `dataset_mailer` (`POSTGRES_MAILER_USER`): SELECT on outbox and UPDATE on delivery columns only. It cannot access identity or products, insert messages, delete them, or change their purpose. Migrations create the roles and grants. After successful migration, `make migrate-up` enables both logins and sets their passwords from `config/.env` in a single transaction; secrets are not stored in versioned SQL.

**Tenancy:** single identity database; no org/tenant tables. **Inferred** as single-tenant until PRODUCT users say otherwise.

**Consistency:** auth multi-step writes use `WithinTx` (register, activate, reset confirm). `RecordFailure` counts in SQL. After hashing outside the transaction, login updates the credential conditionally and inserts its session in one short transaction. The credential row lock serializes this with password reset, which changes the password before revoking sessions. Email cooldown/cap checks and issuance share a transaction lock per user and purpose. Initial sessions and refresh both honor the absolute lifetime.

### Query rules

Every query reads only what its caller uses. A hot path pays for each extra column and each extra row in every request.

- **Name the columns.** No `SELECT *` and no GORM `Find`/`Take` into a full row struct when the caller reads only part of it. A narrower need gets its own method that names its columns (`Sessions().FindLive` for Bearer, next to `FindByID` for refresh). Secrets such as hashes and tokens leave the database only on the path that compares them.
- **Expensive values stay opt-in.** Aggregates that visit many rows (`member_count` on roles) are computed only for the screen that shows them (`FindByID(ctx, id, members)`). `ForUser`, permission checks and batch loops never pay for them.
- **One round trip where one statement can answer.** Several counts over one table use `count(*) FILTER (...)` in one query (`CountRecentFailures`). This matters most inside a transaction that holds locks.
- **Check the cheap thing before the expensive one.** Refuse on a count before loading the rows (audit CSV export).
- **Filters must match the indexes.** A partial index is used only when the query repeats its predicate literally (`shared.CountedFailure`).
- **Read raw SQL with `Find`, `Take` or `Row().Scan`, never `Raw(...).Scan`.** GORM's `Scan` swaps in a recorder logger that formats the full SQL with regular expressions on every call, even with logging off.
- **Request checks share one query.** Routes behind `Require` read the session and the permission bits for that one resource together (`rbac.Access`); the token group middleware (`Token`) only verifies the JWT. Every route in those groups must run `Require` (`TestEveryTokenRouteChecksTheSession`).
- **Bounded caches only.** GORM `PrepareStmt` stays off: its cache has no size limit, and every `IN` list length is a new statement. pgx already caches 512 statements per connection.
- **Every list has a limit.** OFFSET pages and leading-wildcard `ILIKE` are accepted shortcuts, marked `shortcut:` with the size where they stop being enough.

**Auth tokens:** EdDSA (Ed25519), a base64 PEM from `openssl genpkey -algorithm ed25519`; access claims `sub`, `sid`, `jti`, `iat`, `exp`; refresh same with `jti` hashed at rest. Defaults: access 15m, refresh 60m. **Key rotation:** set the new key in `ACCESS_TOKEN`/`REFRESH_TOKEN` and the old one in `ACCESS_TOKEN_PREVIOUS`/`REFRESH_TOKEN_PREVIOUS`; the old key is only verified, never used to sign, and is removed after one refresh lifetime. An access key may never equal a refresh key, current or previous.

**Errors (confirmed):** `pkg/apperror` → JSON `{code,message,field?,details?}` via `rest/mapper`; errors raised by Fiber itself (404, 405, 413) use the same shape. Login failures are always `INVALID_CREDENTIALS`: pending, disabled, locked and unknown accounts answer identically, in the same time. Register answers `201` for known emails too; internal `failure_kind` not echoed.

**User object:** login, refresh and `/v1/me` return the same `user`: identity, `is_superuser`, `permissions` (resource → actions) and `preferences`, loaded live. They are response data for the interface to adapt; the server still decides each request from the database, and the JWT still carries none. If the profile fails to load, login and refresh answer the tokens without `user`, since a refresh has already spent the old token, and the request log records `Request degraded` with the cause.

**Session list:** `last_seen_at` is the time of the last login or refresh, not of the last request: it is not written per request.

**Own-account routes:** the user id comes from the verified token, never from the request, and every query filters by it. Another user's session or notification answers `404`.

**Pagination / idempotency:** `GET /v1/users` and `GET /v1/me/notifications` return `{items, pagination{page,limit,total_items,total_pages}}`; limit defaults to 20, up to 100. Users also take `sort` (allowlist) and `order`. Register is idempotent on email: an unactivated account gets a fresh token, any other answers as new and sends nothing. Outbox rows are append-only inserts (no idempotency key column today).

**Contracts (authz on wire):** Bearer middleware (`/v1/me`, logout) calls `input.Authenticator`, which validates the access JWT + live session. Resource groups use `Token`, which validates the JWT alone; their `Require(resource, action)` calls Authorizer, which checks the live session and the permission in one query (fail closed).

## Control flow

**Sync (request path, confirmed):**

1. **Register** — tx: user `pending` + empty credential + activation token hash + outbox enqueue; optional plaintext token in response if `AUTH_MANUAL_TOKEN_DELIVERY`.
2. **Activate** — validate token and hash outside the transaction; tx: revalidate token → set password → `active` → every enabled default role → mark token used.
3. **Login** — rate-limit checks on attempts → status/lockout → verify password → two-step code when on (no `code` → `MFA_REQUIRED` 401, not a failure; a wrong or reused code counts as a failed password, `failure_kind` `bad_code`) → atomic credential update → create session + issue JWT pair → record attempt. TOTP is RFC 6238 (SHA-1, 30 s, 6 digits, ±1 step); the secret is sealed with the SMTP master key, each step logs in once (`usr_mfa.last_step`), recovery codes are SHA-256 hashed and single-use. `admin mfa-reset` turns it off for a user who lost the phone and the codes.
   **Single sign-on** — the web app's `/api/auth/sso/start` asks the backend for the provider address and a sealed flow (state, nonce, PKCE verifier, 10 min), keeps the flow in an httpOnly cookie and redirects; `/api/auth/sso/callback` sends code, state and flow back. The backend checks the state against the flow, trades the code (PKCE), verifies the ID token and its nonce, and needs `email_verified`. It logs in only an existing, active, unlocked account with that email, never creates one, and leaves two-step login to the provider.
4. **Refresh** — parse refresh → load session by `sid` → reuse detection / compare-and-swap rotate → new pair. Each refresh extends the session, never past `AUTH_SESSION_MAX_LIFETIME` (30 days) from login. A lock does not stop refresh. The token rotated in the last 10 s answers `409`, without revoking: the client reads the winner's token and retries.
5. **Logout** — Bearer resolves the session → revoke it (`user_logout`).
6. **Password reset** — request enqueues outbox; confirm hashes password, revokes all sessions, marks token used.

**Notifications:** written by the auth use case for password changed (same transaction as the reset), account locked, refresh token reuse and login from a client never seen on the account (best effort: a lost notice does not fail the login). Clients poll. First login notifies nothing; after it, a client with no session left on the account counts as new. The integration use case adds `webhook_paused` (a hook paused after 10 failures; `url`, `collection`) and `automation_error` (an automation whose last run worked now fails; `automation`, `error`), each to the maker. Each one carries a `kind` (`new_login`, `account_locked`, `session_reused`, `password_reset`, `password_changed`, and those two) and string `params` (`ip`, `until`); the web app writes the text in the user's language from them. `title`/`message` stay as English fallbacks.

**Emails:** plain text in the user's saved language (Portuguese by default, English otherwise), chosen when the email is queued. The link carries the token in the URL fragment (`/activate#token=...`), which never reaches a server log or a `Referer` header; the web app reads it and clears the address bar.

**Async (confirmed):** mailer claims outbox with `SKIP LOCKED`, sends SMTP (or terminal `smtp_disabled`), backoff on retryable failure.

**Health:** Postgres ping (`ok` / `down`), reused for 1 s. One request probes at a time; the others answer the last report, `down` until the first probe ends.

## Failure domains

**Confirmed what fails together:**

| Domain | Behavior |
|--------|----------|
| Postgres down | Backend/mailer boot fails; health `postgres=fail` |
| Fiber timeouts | `API_READ/WRITE/IDLE_TIMEOUT` (30s/30s/120s); shutdown `API_SHUTDOWN_TIMEOUT` 30s |
| Login abuse | DB-backed attempt counters per client+account (5), client (`/64` on IPv6) and account (50) → `TOO_MANY_REQUESTS` with `Retry-After` (seconds until the oldest counted failure leaves the window); lockout at 50 answers `INVALID_CREDENTIALS`. One client cannot lock the owner out. Each attempt is reserved under an advisory lock before hashing, so parallel requests cannot outrun a limit. Passwords need 8 to 128 bytes and may not be a common first guess, one repeated character, or the account's own name or email. A password reset request answers no sooner than 300 ms, so an unknown email is not told apart by timing. `AUTH_ALLOW_REGISTRATION=0` closes public sign-up and leaves invitations only (register answers 403). |
| Memory | Body limit 8 MiB + 4 KiB (an attached file is the largest body; the web proxy refuses larger first); at most 4 Argon2 hashes (256 MiB live); `GOMEMLIMIT` and container limits in compose; Argon2 runs outside transactions; waiting for a hashing slot is cancellable, but a running Argon2 calculation finishes. PHC version, costs, salt and digest lengths are bounded before allocation |
| Email flood | `AUTH_EMAIL_TOKEN_COOLDOWN` (60 s) and `AUTH_EMAIL_TOKEN_HOURLY_MAX` (5) per account and purpose; over the cap the live link survives |
| Refresh reuse | Session revoked `token_reuse` |

**HTTP limits:** `API_RATE_LIMIT_*` per client IP (IPv6 by `/64`) per minute, counted in the UNLOGGED table `sys.rate_limit` with one atomic upsert per request, so every instance shares the limit. The hourly cleanup (`sys.fn_cleanup`) drops past minutes. A counter failure answers 500. Login and email limits also live in Postgres.

**Not implemented (confirmed):** separate DLQ table (terminal fails stay on outbox as `failed`).

**Webhooks (outbound HTTP, off the request path):** the sender dials only public addresses, checked on the resolved IP at connect time (no loopback, private, link-local, CGNAT, multicast; `WEBHOOK_ALLOW_PRIVATE=1` lifts this for local tests), follows no redirects and gives up after 15 s. Jobs run one at a time, so each failing call holds the queue up to 15 s; ten in a row pause the hook.

## Observability

**Confirmed:** zerolog via `pkg/logger`; base fields `version`, `service` (`backend`|`mailer`), `pid`. Boot logs host/port/env/errors.

**Confirmed:** `RequestLog` uses Fiber's zerolog integration for ordinary requests and returned errors, with a wrapper for internal causes stored in `mapper.LocalCause`. It records 5xx responses at error level and degraded answers at warning level even when `API_LOGGER=0`; enabling `API_LOGGER` also records ordinary requests. Each request produces at most one request-log entry. Fields include status, method, client IP, latency, PID, path and `request_id`; query strings, headers and bodies are omitted. Internal application-error causes stay in the log and are not added to HTTP responses. The auth use case logs a warning when a best-effort step fails (attempt settlement, notification).

**Correlation id:** `RequestID` gives each request an id, returned in `X-Request-ID`. An incoming id is kept only from a trusted proxy. `pkg/reqctx` carries it, with the authenticated user, through the context: into the request log, `sys.outbox.request_id` (logged by the mailer) and the audit log.

**Audit log:** `sys.audit_log` records role, permission, membership, user status, unlock, invitation and its resend, session revocation and collection changes from the API and `cmd/admin`, through `policy.Audit` in the transaction of the change. A NULL actor means the CLI. The app role may only insert. `GET /v1/audit` reads it (`audit:read`); there is no cleanup. The list total stops at 10 001 (one past the export limit), so a filter that matches more reads as "more than 10 000" instead of counting the whole log.

**Diagnostics:** `DIAGNOSTICS_ADDRESS` defaults to `127.0.0.1:9091` inside each container. `/metrics` returns JSON with bounded HTTP latency buckets, server errors, hashing queue/active counts and wait time, `database/sql` pool statistics, outbox count/oldest age and runtime heap/GC counters. `/health` checks PostgreSQL and, for the mailer, a successful worker heartbeat within one minute. `/metrics/prometheus` serves the same numbers, plus the job queue, in the Prometheus text format for a scraper on that network. No public API route exposes these diagnostics. Compose uses healthchecks and stop grace periods of 40s (backend) and 60s (mailer).

**Absent:** distributed tracing. Add OpenTelemetry when a second service joins the request path.

Do not log refresh tokens, passwords, or email token plaintext (payload in outbox is sensitive — treat as secret storage until mailed).

## Delivery

**Confirmed:**

- Release: `make deploy` (in `backend/`) runs the steps in their order: start postgres and backup, `make db-backup`, `make migrate-up`, rebuild backend and mailer, rebuild the web. Each build is also tagged with its commit (`git describe --always --dirty`), so `SYS_VERSION=<commit> make compose-up` (backend) or `WEB_VERSION=<commit> make compose-up` (web) starts an older one; the web image carries it as `BUILD_REVISION`
- Schema: `make migrate-up` runs `golang-migrate` in a temporary container sharing the Postgres network namespace. It mounts `deploy/db/migrations` read-only and configures the database logins after the migrations succeed.
- Runtime: Docker Compose (`deploy/docker/compose.yml` + `services.compose.yml`: postgres, backend, mailer; app containers run as `nobody`, with no Linux capabilities and `no-new-privileges`; the API port is published on `127.0.0.1` only, the web reaching it over `dataset_network`). The mailer gets throwaway JWT keys (`ACCESS_TOKEN=new`, `SYS_SERVICE=mailer`), and no inherited backend database password; its database role is restricted to outbox delivery
- Dev: Air (`make dev-backend` / `dev-mailer`); binaries `make build-*`
- Config: `config/.env` from `config/env.sh` / `make init`
- `make compose-build` recreates the backend and mailer containers after the build, so a rebuilt image under the same tag always runs (the web Makefile passes `--force-recreate`)
- Backups: the `backup` service waits for `schema_migrations` to reach the latest bundled migration with `dirty = false` before its first scheduled dump. It runs `deploy/docker/backup.sh`: daily, it dumps the database (`pg_dump -Fc`), tars the file store, restores the dump into a scratch database (`<base>_restore_check`, dropped after) and reads the archive back; a backup that fails any step is logged `FAILED` and old ones are kept. Each verified backup touches `.last-ok`; the container turns unhealthy when it is over 26 h old. It keeps `BACKUP_KEEP_DAYS` (7) in `BACKUP_DIR`, a host folder (an external disk, a synced or network folder) or, when empty, `dataset_backup_volume` on this disk, which dies with it. `make backup-now` and `make backup-verify` run it by hand; `make db-backup` dumps into `backend/backups/`; `make db-restore FILE=...` restores one over the current data

**CI:** vet, tests with `-race` and Postgres, lint, `govulncheck`, and a check that `make swagger` changes nothing.

**Rollback:** SQL `*.down.sql` per migration; no feature-flag system in code. **Inferred:** expand/contract discipline is human/process, not automated.

**`cmd/admin`:** operator CLI in the backend image. `make admin-bootstrap`, or `./bin/admin` with no argument on the host, asks name, email and password and creates the first admin, active, with no email involved; it does nothing once any admin exists, and refuses an email already in use. The password is never an argument: hidden on a terminal, one line per value on a pipe. `make admin-promote` asks the email and gives that active user the `admin` role; `make admin-disable` asks the email, disables that user and revokes their sessions; `make admin-enable` lifts that. `cmd/admin` is the only way to change a user with a protected role.

**Behind a reverse proxy:** set `API_TRUSTED_PROXIES` and keep `API_PROXY_HEADER` on a header the proxy overwrites (`X-Real-IP`), or use `X-Forwarded-For`, read from the right past the trusted proxies.

**External database:** protected environments refuse a non-local Postgres host unless `POSTGRES_URL` uses `sslmode=verify-full`.

## Cost hotspots

**Suspected (no measurements — see PRODUCT.md Unknown cost posture):**

- Argon2id verify on every login (`time=3`, `memory=64MiB`, 4 threads in `pkg/password`)
- Each permission check → one query, no cache
- Login attempt inserts + rate-limit counts
- Login, refresh and `/v1/me` each run user + permissions + preferences queries (roles without member counts)
- `search` is a leading-wildcard `ILIKE`, and lists use `OFFSET` plus a count: scans grow with the table. Measured on records (100 000 in one collection, 2026-11): first page 0.04 ms, search 0.5 ms (trigram index), exact filter 16 ms, number range 27 ms, sort by a field 43 ms, page 3 600 56 ms. Per-field indexes and keyset paging wait for ~1 000 000 records

## API docs

Swagger UI at `/swagger/index.html`, outside protected environments only. Handlers under `rest/handler` carry `swag` annotations and `make swagger` regenerates `internal/adapter/inbound/http/rest/docs/docs.go`. Each handler package mounts its own routes (`Routes`); every operation has one `@Tags` tag, by subject; `x-tagGroups` in `rest/swagger.go` groups the tags, rendered by the plugin in `rest/docs/swagger.js` as collapsible sections, closed by default. Every operation also has a unique `@ID` (package then action, e.g. `webhookCreate`), lists the failures it can answer (401 when secured, 403/404 on collection and id routes, 400 with a body, 429 everywhere but `/health`, which sits before the global limiter), and models carry `// @name` (`Webhook`, `RecordCreateInput`) so the spec shows no Go package names. Routes that accept an API key list `BearerAuth` and `ApiKeyAuth`. Custom styles live in `rest/docs/swagger.css`. `swagger_test.go` fails when a route and the docs disagree, or when an operation's tag has no `@tag.name` and place in `x-tagGroups`.

An icon-only theme toggle sits at the right of the API title, on the same line. The first visit follows the system theme; the selection is saved in browser local storage when available. The button has a tooltip, supports keyboard activation and exposes its accessible name and state with `aria-label` and `aria-pressed`.

## Known gaps vs intent

1. **Observability thin** — correlation id and audit log, but no traces.
2. **Scale and SLOs unmeasured** — no measured throughput, latency or availability targets; the shared rate limiter costs one database write per request.

## Boundaries and verification

Application services use a small logging port, a protected email payload codec and shared identity policies. AES and the JSON outbox format live in `adapter/outbound/emailpayload`. The admin CLI consumes `input.AdminService`. Non-transactional account/user/role dependencies expose only the needed repositories; transactions keep one UnitOfWork so operations still share a single database connection. Generic transaction locks belong to UnitOfWork, not login attempts.

Authentication is split into login, refresh, request authentication, session insertion, attempt limits and notifications. Integration scenarios live under `tests/integration`, while pure policies and handlers keep focused tests beside their code. `tests/architecture` guards dependency direction. SQL record maintenance timestamps use the database/runtime clock; login attempt and email token issuance times, expirations and session rules use the application Clock. Health TTLs and diagnostic heartbeats intentionally use elapsed real time.


Benchmarks: `go test -run '^$' -bench BenchmarkHashParallel -benchmem ./pkg/password`. Use deployment measurements before claiming capacity or changing cryptographic cost.
